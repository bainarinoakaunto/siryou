2. 集計方法と計算根拠

  • 読み込み：タブ区切りテキスト（UTF-8）としてそのまま読み込み。1行目のヘッダー行と、タブのみの空行13行をレコード数から除外しました。データ行は 1816行（全行7列で欠損セルなし）。
  • タイムスタンプ：「タイムスタンプ」列（1列目）を基準に整形。形式は「YYYY/M/D H:MM（:SSあり/なし混在）」で、全1816件をエラーなく日時型に変換できました。
  • 重複の定義：7列すべて（タイムスタンプ・アクセス日時・URL・タイトル・端末・OS・ブラウザ）が完全に一致するレコードを「重複」とし、2件目以降を除いて「重複除去後」の値を算出。84組の重複グループから127行の余剰が見つかりました（例：2026/10/03 7:32:36〜41 の /status への連続記録は同一内容が2〜6連続）。秒まで同一の連続記録は同一閲覧の二重記録の可能性が高い一方、日時が異なる別記録は「実際のアクセス（再訪・再読込）」として区別し重複には数えていません。
  • ページの集計：URLの末尾スラッシュのみ正規化（example.com/ と example.com を同一扱い）。それ以外の表記ゆれ（/index と /index.html、/status と /status.html など）は意図的に統合していません（元データを変更しないため）。そのため「実質同一ページ」の合計は本文中で参考値として併記します。
  • 404の判定：HTTPステータス列は存在しないため、「ページタイトルに『404』を含む」または「URLに『404』を含む」レコードを404閲覧と判定（タイトルは一貫して「404 | BINARY」）。該当 246件（生）／197件（重複除去後）。
  • 端末・OS・ブラウザ：ログの専用列をそのまま集計（UA文字列からの推測は行っていません）。空白セルは「不明」扱いですが、実際の欠損は0件でした。表記ゆれ（iOS / iPadOS・iOS/iPadOS・iOS など）は列ごとの分類表では元表記のまま、考察欄での合計値のみ参考として併記しています。

11. アクセス傾向の総括

  • 障害告知がトラフィックを牽引：10/3〜10/6と10/9の急増は、株シミュレーター関連の稼働状況（/status）・お詫びPDF・ニュースページへの集中と一致します。トップ10日の上位4日はすべてこの時期です。
  • 平日昼＋夜間の常連型：学校・職場時間帯（7時・昼12時・16〜17時）と夜（22〜23時）の二峰性は、Chromebook中心の利用者層を示唆します。
  • 繰り返し閲覧が多い：重複除去で約7%減（1,816→1,689）にとどまる一方、30分区切りで231グループ＝1回の訪問まとまりで平均7.9ページ閲覧。短期集中型の閲覧（障害確認など）が多い構造です。
  • 課題：①リンク切れ404が全アクセスの13.5%（特に数字URLと日本語ファイル名PDF）、②iOS端末でのブラウザ分類の不明、③/statusへの再読み込み集中、が改善余地として挙げられます。

12. データの限界（必読）

  • 記録数は訪問者数ではありません。ユニークビジター・離脱率・滞在時間・流入元は本データからは算出できません。
  • 本ログは自己記録型（閲覧側スクリプト等による記録）と思われる列構成であり、ボット/クローラーと人の判別は不可能です。
  • タイムスタンプとアクセス日時のわずかな差（1〜2秒）は記録処理によるものと考えられますが、タイムゾーンの明記はデータ内にありません。
  • 集計は提供ファイルのコピーに対して読み取り専用で行い、元データは一切変更していません。
